# Webhook protocol, version 1

Hooks are trusted external services, not in-process Rust plugins.
Only an Owner or Admin can change them. Do not attach an untrusted
service: synchronous hooks receive request and response bodies.

## Request

Tokomotive sends a POST with `Content-Type: application/json`:

```json
{
  "version": 1,
  "stage": "pre_request",
  "hook": "policy",
  "request_id": "server-generated opaque ID",
  "timestamp": 1794787200,
  "data": {
    "endpoint": "chat_completions",
    "route": "chat",
    "model": "chat",
    "body": {"model": "chat", "messages": [{"role": "user", "content": "Hello"}]},
    "key_id": 7,
    "team_id": 2,
    "user": "alice",
    "metadata": {"x-tokomotive-meta-project": "research"}
  }
}
```

The request ID is generated by the server. It is the same for all stages
of one request. `route` and `team_id` can be null. The metadata allowlist
is `x-tokomotive-meta-project` and `x-tokomotive-meta-environment`.
Each value has a 1024-byte cap. Other headers, including authentication
headers, are not sent.

`post_response` data contains `request` (the request context above), `body`
(the response JSON), and the upstream `status`. It runs only on successful
non-streaming JSON responses. Streaming requests skip this stage. A hook
with only `post_response` does not block a stream.

`event` data contains `ledger_id` and `ledger` (the final Ledger Entry).
The entry includes usage, Cost, Price and final status, including a hook
or guardrail rejection. Events also apply to streams. They do not contain
prompt or response bodies by default. **Include bodies in events** adds
`request` and `response`. The response is captured after response guardrails;
a stream is captured as SSE text. Each body has a 1 MiB cap. A body over
the cap is null and `bodies_omitted_over_cap` is true. Hook diagnostics do
not store bodies.

The signed sample from **Test signed sample** has `data.test: true` and
sample identities. It does not use a real prompt or call a Provider.

## Signature

The headers are:

```text
x-tokomotive-hook: policy
x-tokomotive-signature: t=<unix-seconds>,v1=<hex-hmac-sha256>
```

The HMAC key is the exact secret string shown at creation or rotation.
Do not hex-decode that string. The signed bytes are the decimal timestamp,
a dot, then the exact HTTP request body bytes: `t.body`. Do not parse and
serialize the body again before verification.

This Python example verifies the signature and checks a five-minute
time window:

```python
import hashlib
import hmac
import json
import time


def verify_hook(raw_body: bytes, signature: str, hook_header: str, secret: str):
    fields = dict(part.split("=", 1) for part in signature.split(","))
    timestamp = fields["t"]
    if abs(int(time.time()) - int(timestamp)) > 300:
        raise ValueError("Expired hook signature")
    signed = timestamp.encode("ascii") + b"." + raw_body
    expected = hmac.new(secret.encode("ascii"), signed, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, fields["v1"]):
        raise ValueError("Invalid hook signature")
    envelope = json.loads(raw_body)
    if (envelope["version"] != 1 or envelope["timestamp"] != int(timestamp)
            or envelope["hook"] != hook_header):
        raise ValueError("Invalid hook envelope")
    return envelope
```

Use HTTPS and keep the secret private. For replay protection, atomically
retain accepted `(hook, request_id, stage)` values for the accepted time
window. Rotate the signing secret if it is exposed.

## Decisions

Return a successful HTTP status and one of these JSON objects for a
synchronous stage:

```json
{"decision": "continue"}
```

```json
{"decision": "modify", "patch": {"temperature": 0.2}}
```

```json
{"decision": "reject", "status": 422, "message": "Request does not meet policy."}
```

`patch` must be a JSON object. It uses JSON Merge Patch (RFC 7396): objects
merge, null removes a field, and arrays replace the entire array. A
pre-request patch applies only to the body. It cannot change authentication
headers, key identity, Team, endpoint, resolved Route or selected
Deployments. A change to `model` is the one exception: the server checks
model permission and resolves the new model and Provider again. Provider
Access still applies. All request limits are checked again.
Multipart uploads can continue or reject, but cannot be modified.

A post-response patch changes only the JSON response body, not the status
or headers. Upstream usage and Cost remain in the Ledger even if a hook
changes usage fields or rejects the response. `reject.status` must be
400 through 499. The message must not exceed 4096 bytes.

Events ignore decisions. Return any 2xx status to acknowledge an event.
Delivery is best effort, with no retries or durable queue.

## Limits, order and failures

Hooks run in increasing priority, then by name. Attachments form a union:
one hook attached at multiple matching scopes runs once per stage.
At most 64 hooks can be stored.
The hook list is selected once from the original resolved Route and
authenticated identity. A permitted model change does not select a
second hook list or run pre-request hooks again.

Pre-request hooks run after authentication, rate admission, Budget
admission and request guardrails, and before cache lookup. The modified
body determines the exact and semantic cache identity. Budget admission
for the modified request still applies before the Provider call.
A model change does not consume a second request-rate admission.

Post-response hooks run before response guardrails. If any enabled
post-response hook is attached, the response is not stored in either the
exact cache or the semantic cache, including for a streaming request.
Existing entries can still be read; response hooks still apply to hits.

The default timeout is 2000 ms. The maximum is 30000 ms. This timeout
includes DNS, connection, headers and the complete response body.
Responses have a 1 MiB cap. Redirects, non-2xx responses, invalid decisions
and responses over the cap are failures. Fail open continues on these
failures. Fail closed returns a 502 error. An invalid request patch is
always rejected, including with fail open.

Use HTTPS. A hook's private-address permission permits private HTTPS and
HTTP to private or loopback addresses. Public HTTP is refused, including
when private-address permission is selected. Address checks and direct
DNS pinning use the secret-store network policy. The global egress proxy
setting applies when configured.
An HTTP or remote-DNS SOCKS proxy resolves hostnames itself. As with the
existing secret-store and MCP transports, that proxy must enforce the
address policy and prevent DNS rebinding. Direct DNS pinning cannot
control the proxy's resolver.
The Owner configures this trusted proxy; local private/loopback checks
still run on literal IPs and locally resolved hostnames before each request.

The event queue holds at most 64 waiting calls, with at most 4 active
calls. A full queue drops new events. The metric
`llm_hook_events_dropped_total{hook=...}` counts drops.
`llm_hook_calls_total` and `llm_hook_duration_seconds` have hook, stage
and outcome labels. Outcomes include `continue`, `modified`, `rejected`,
`error`, `timeout`, `rejected_error` and `rejected_timeout`.
The `hook_calls` table retains only the newest 10000 calls. It contains
names, stages, outcomes, durations, HTTP status and Ledger links, not
bodies, URLs or secrets.
